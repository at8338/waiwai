# チームごとのサーバー

Waiwaiの「サーバー」は、同じアプリ・同じAzure VMで動かす独立したオフィスです。追加のたびにVM、ドメイン、Terraform環境を作る必要はありません。サーバーごとに全フロアを持ち、所属するメンバー同士だけが会えます。URLの`?space=<ID>`は入室先の指定であり、招待券や権限ではありません。

## 管理者の操作

1. 本人確認済みの管理者でログインする。管理権限は[管理者モード](admin-mode.md)と共通。
2. 上部の「サーバーを選ぶ」、または「管理者モード」→「サーバーと所属を管理」を開く。スマホでは「メニュー」→「サーバーを選ぶ」。
3. サーバー名を入力して追加する。作成直後のサーバーには一般メンバーの所属はない。
4. 参加者に一度ログインしてもらう。初めてログインした人は「所属未設定」となり、管理者のメンバー一覧に表示される。
5. 「メンバーの所属」に切り替え、名前・アカウントIDで検索し、入室を許可するサーバーにチェックして「所属を保存」。複数所属も、所属なしも設定可能。

管理者は公開中の全サーバーに入室できる。一般メンバーには許可された公開中のサーバーだけを表示する。名前変更・非公開化にも対応し、データを誤って失わないよう削除機能は設けていない。サーバーは最大50個。非公開にした場合や所属から外した場合は、対象サーバーへの全タブの接続を終了し、音声の接続先からも外す。少なくとも1つのサーバーを公開しておく。

メンバーの識別は検証済みログインの不変ID（Microsoftのテナント＋Object ID、Slackのワークスペース＋ユーザーID）を使う。表示名や自己申告のメールアドレスでは所属を付与しない。同じ人物でも別のログイン方式は別アカウントとして扱う。今回の機能はログイン後の所属管理で、Entraへの招待・メール送信は行わない。

## 分離する範囲

サーバーごとにWebSocket接続、アバター、人検索・オンライン一覧、ワープ・コール、音声の接続許可、全館／フロア／グループ／DMチャットと既読、家具・小物、共有URL、誕生日・お祝い、放送・予定、ゲーム・闘技場、乗りもの、事件の現在状態、出現テスト、表示許可ポリシーを分離する。「全館」は現在のサーバーの全フロアを指し、他のサーバーへ配信しない。日付由来の事件や出現候補は同じ日には同じものになる場合があるが、管理操作や同期の状態は共有しない。

見た目・バディ・図鑑や事件の発見記録は個人アカウントに保存するため、サーバーを切り替えても引き継ぐ。切り替え時は保存待ちの個人設定の完了を待ち、ページを読み直して音声・チャット・マップを新しい接続で開始する。入室中のサーバーはタブごとのURLで決まり、別タブの入室先に影響しない。

全ユーザーの名簿は管理者が所属を設定するためにサーバー内で共有するが、一般メンバーへの人検索にはそのサーバーの所属者だけを載せる。所属解除で過去の保存データを消すことはなく、再所属時にはそのサーバーでの記録を再利用できる。

Slackの既存`#waiwai`連携は最初の`default`サーバー専用。追加サーバーでは外部へのチャット転送を無効にしており、既存の共有URLや履歴もコピーしない。`default`のSlackチャンネル参加者には、そのサーバーから明示共有した発言が見えるので、チャンネルのメンバーを所属の運用に合わせる。サーバーごとのSlack連携設定は今後の拡張対象。

## 既存データと保存先

初回起動で`office-spaces.json`を作り、既存メンバー名簿に載っていた人だけを`default`（初期名Waiwai）へ所属させる。初回移行は名簿への新規登録より先に保存し、再起動時には繰り返さない。既存の家具・チャットなどの保存先はそのまま`default`のデータとして使用する。開発モードの未ログインゲストは`default`だけに入り、本番の入室にはログインと所属を必要とする。

- レジストリ：`WAIWAI_SPACES_FILE`。省略時は`WAIWAI_DATA_FILE`のディレクトリの`office-spaces.json`。
- 全体名簿：既存の`WAIWAI_MEMBERS_FILE`。本人確認済みのアカウント情報だけを記録する。
- `default`：既存の`WAIWAI_*_FILE`設定を維持。
- 追加サーバー：`<WAIWAI_DATA_FILEのディレクトリ>/spaces/<サーバーUUID>/office-*.json`と`office-chat.sqlite`。
- 個人データ：既存の`WAIWAI_PERSONAL_FILE`を全サーバーで利用。

レジストリの変更は直列化し、リビジョンで別画面からの上書きを防止する。一時ファイルを書いてから置き換え、保存失敗時は所属を変更しない。破損した設定を「制限なし」にして起動しない。管理者の不変IDは明示設定または初回の本人確認時に固定する。ブラウザの指定、URL、プロフィールから管理権限や所属を追加できない。

Azureでは既存の永続ディスク`/var/lib/waiwai`内に追加サーバーも保存するため、現在のVMバックアップ対象に含まれる。個別にSQLiteをバックアップする運用では、`spaces/*/office-chat.sqlite`も既存のスナップショット用スクリプトの対象に含める。稼働中のSQLite/WALを単純コピーせず、停止して保存するか、各DBのスナップショットを取得する。

## 容量とインフラ

プロセスは入室されたサーバーのオフィスを必要に応じて起動し、独立した状態と保存先を持つ。同じVM・ディスク・障害範囲・TURNサービスを共有する論理的な分離であり、サーバーの追加でCPU・メモリ・通信容量は増えない。既存の150人の入室制限は各オフィスに残るが、これは共有VMで全サーバーそれぞれ150人を処理できるという性能保証ではない。従来の「合計150人・音声30人」を超える運用では、全サーバーの合計負荷で試験して増強を判断する。

別会社ごとに独立した障害範囲・管理権限・契約上の分離が必要になった場合は、別VM・別データ領域・必要に応じて別Azure環境へ配置する。その場合もアプリのサーバーIDや所属モデルを再利用できる。今回の実装ではTerraform apply、Azureリソースの作成、デプロイは実行しない。
